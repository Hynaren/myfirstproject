# Daily Quest — Gather Resources (Food / Stones / Timber / Ore / Gold)

## Status

Design checkpoint. This document defines the shared routine and the validation plan.
Do not mark this quest as live-tested until Search navigation, templates, and troop dispatch
have been verified on LDPlayer.

## Daily Quest definitions

The existing `quests/definitions.py` contains these exact quest IDs and targets:

- `gather_food`: Gather Food from Fields on the Kingdom Map — 100000
- `gather_stones`: Gather Stones from Rocks on the Kingdom Map — 100000
- `gather_timber`: Gather Timber from Woods on the Kingdom Map — 100000
- `gather_ore`: Gather Ore from Rich Veins on the Kingdom Map — 100000
- `gather_gold`: Gather Gold from Ruins on the Kingdom Map — 35000

All five IDs should use one shared `GatherResourcesRoutine`, configured by resource type
and quest target. Keep the exact existing quest IDs and display names.

## Confirmed World Map behavior

- The game has a coordinate Search: enter X/Y and the map moves the searched location to the
  center of the screen.
- The player's Castle coordinate is the starting point for choosing the initial search area.
- After moving to a search coordinate, inspect the center and visible surrounding area before
  panning.
- The map contains mixed resource tiles, so the routine must verify the selected tile's
  resource type instead of assuming that a nearby tile matches the quest.

## Architecture

AutomationEngine
-> Global Popup Safety
-> QuestManager
-> GatherResourcesRoutine
-> WorldNavigation / ActionEngine
-> Detector / Vision
-> ADBController

The routine must not call ADB directly. Popup handling remains owned by the existing
AutomationEngine / PopupManager pipeline.

## Routine contract

Proposed routine configuration:

- `resource_type`: `food`, `stone`, `timber`, `ore`, or `gold`
- `quest_target`: 100000, except gold = 35000
- bounded local-search limits and swipe parameters, configurable for unit tests

Suggested responsibilities:

1. Confirm or navigate to the World Map using the existing WorldNavigation contract.
2. Obtain the player's Castle X/Y from the in-game UI. Do not guess coordinates or hardcode
   a player's location.
3. Open the game's coordinate Search, enter the selected X/Y, and submit.
4. Wait for the map to settle and verify the World Map is visible.
5. Detect the target resource in the current centered viewport and nearby visible area.
6. If no valid target exists, pan gently in a bounded 8-direction search pattern. After each
   swipe, wait, capture a fresh screenshot through ActionEngine, and detect again.
7. When a candidate is found, tap the detected candidate and inspect the resource information
   panel.
8. Verify resource type, level if relevant, and that the tile is unoccupied / gatherable.
9. Tap Gather only after the information panel confirms a valid target.
10. Verify the troop-selection / march UI, choose a valid troop configuration, and confirm.
11. Verify that the march started or that the game's quest progress changed. A successful tap
    alone is not proof of completion.
12. Return success only when the game's observable state confirms the expected action or
    quest completion. If progress requires time gathering, report that the march started rather
    than claiming the entire resource target was collected.
13. If no valid target is found within the configured search bound, stop safely and return
    failure; never pan indefinitely.

## Search strategy

- Starting anchor: player's Castle coordinate.
- Search target: an X/Y coordinate selected relative to that anchor.
- The game's Search centers the selected coordinate on screen.
- First inspect the center and current viewport.
- Then search locally in eight directions: N, NE, E, SE, S, SW, W, NW.
- A swipe's finger direction is opposite the map region revealed; calibrate and test the
  swipe mapping before production use.
- Use a deterministic, bounded order and track already-scanned directions/areas within one run.
- Re-detect after every pan; never reuse screen coordinates from a prior viewport.
- Do not repeatedly search the same area when a resource is occupied or unsuitable; mark that
  candidate as skipped for the current run.
- The exact X/Y step size, swipe endpoints, duration, and whether Search UI exposes the
  player's Castle coordinate must be confirmed against the current 960x540 LDPlayer screen.
  Do not invent these values in production code.

### Coordinate entry procedure

1. Tap the Search icon and verify the Search panel.
2. Tap X field to open the numeric keypad.
3. Replace the existing X value using the keypad backspace control, enter the desired digits,
   then tap the green check.
4. Tap Y field and repeat.
5. Verify the displayed X/Y values where possible, then tap Go.
6. Wait for map movement to settle and confirm the selected coordinate is centered.
7. Never assume keypad input succeeded merely because taps returned success.

The keypad is an in-game numeric keypad; do not use desktop keyboard input unless separately
verified. Since coordinate values vary, clear/replace the currently displayed digits safely
instead of assuming a fixed digit count. Test whether the backspace button removes one digit
per tap and what the UI shows for zero before enabling automated entry.

## Safety and failure handling

- Required templates missing: fail before interacting with the game.
- Search panel not detected or coordinate submission not verified: stop without panning.
- Candidate type cannot be verified: do not Gather.
- Occupied, unavailable, or unsuitable tile: skip it and continue within the bounded search.
- Swipe or tap failure: stop the current step and report failure.
- Troop selection / march confirmation not detected: do not repeat Gather blindly.
- Popup handling remains centralized in PopupManager.
- Never use stale screen coordinates after Search or swipe.
- No OCR assumptions, account-specific coordinates, or fabricated map positions.
- Quest progress is sourced from game UI; the routine must not calculate completion solely
  from the number of successful taps.
